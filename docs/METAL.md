# Metal GPU バックエンド

CLI・常駐APIで共通の推論エンジンを使い、BF16行列演算と、必要な行列を保持した場合の生成全体をApple SiliconのGPUで処理します。元のsafetensorsをそのまま使います。キャッシュの圧縮でも元の全16ビットを保持し、重みファイルの変換は行いません。アセンブリだけのCPU実装は`plamo-asm`です。

## 起動と選択

```sh
make all
python3 tools/server.py --backend metal --memory auto
# metalと同じFP32経路（互換名）
python3 tools/server.py --backend metal-fp32 --memory auto
# CPUの性能コアで計算する場合
python3 tools/server.py --backend cpu --memory auto --threads 4
```

`--model 0.8b|2b|8b|31b`も併用できます。別サイズは先に`make MODEL=2b all`などでビルドします。既定の`--backend auto`は利用可能なMetal GPUを選び、初期化できなければCPUへ戻ります。`metal`・`metal-fp32`の明示指定ではGPUの初期化失敗を起動エラーにします。GPUが常にCPUより速いという判定や自動チューニングは行いません。

`GET /health`の`compute`に実際の`backend`・`device`・`precision`、GPU実行回数、CPUへのフォールバック回数、エラー数、累積GPU時間を表示します。`allocated_bytes`はMetalが報告するリソース確保量、`recommended_working_set_bytes`はデバイスの推奨量です。これらはCPUプロセスのRSSとは別に確認してください。`--threads`はCPUバックエンドの設定で、GPUの並列数ではありません。

## 計算精度

| バックエンド | 保持する重み | 行列演算のオペランド | 累積・入出力 |
| --- | --- | --- | --- |
| `cpu` | 元のBF16 | FP32 | FP32 |
| `metal` / `metal-fp32` / GPU選択時の`auto` | 元のBF16 | FP32 | FP32 |

FP16への丸めを削除し、入力の長さによらずFP32に統一しました。BF16からFP32への展開はビットのシフトだけで、元の値を正確に保持します。生成では隣接するSIMDレーンが同じ行の隣接列を読み、SIMDグループ内で和を取ります。4〜7入力トークンでは各BF16ロードを共有し、8トークン以上は入力長に合わせた32行×8/16/24/32トークンのSIMD-group行列タイルを使います。内部のKタイルは32列です。計算が済んだ重みタイルを出力の転置にも再利用し、共有作業領域はタイルに応じて5〜8 KiBです。GPUの行列演算APIは[Appleの解説](https://developer.apple.com/videos/play/tech-talks/10858/)も参照してください。

GPUでは加算順序が異なるためCPUとのビット一致は保証しません。翻訳を決定するモデルは追加の量子化・低精度化を行いません。元のCPU参照に対する全logits・最終状態の相対L2誤差と、生成トークン列を検証します。

## 8Bの候補検証による生成

8BのMetal生成では、0.8Bワーカーとその重みが利用できれば候補検証を自動で有効にします。補助モデルは8トークンから候補を作り、全候補が採用されれば最大16まで伸ばします。長い候補は補助モデルの上位2トークンのlogit差が小さければ8以上の位置で打ち切り、先頭直後の棄却では次の候補数を2に減らして段階的に戻します。8Bが元のBF16重み・FP32演算で一括計算し、8Bのgreedy選択と一致する接頭だけを採用します。不一致位置のトークンは8Bが選びます。確定前のKVは別領域に置き、採用した分だけ既存のKVへ反映します。棄却した候補が後の生成に混ざることはありません。

候補の作成時間を短縮するため、**補助モデルだけ**は32値ごとのQ4をGPUメモリ上で作ります。隣接する2コードを1バイトに収め、単一トークンの正規化・SwiGLUと同時にFP16の入力コピーを作ります。整数係数と入力の積和はFP16、ブロックのスケールとブロック間の集計はFP32です。通常のFP32入力も残し、端数や複数入力の処理に使います。埋め込みは元のCPUマッピングから参照し、使わないQ4コピーを作りません。元の0.8Bファイルと8Bの重みは変更しません。補助モデルの誤りは候補の採用率に影響し、最終トークンは8Bで検証します。8Bの一括行列計算はFP32の加算順序が逐次生成と異なるため、通常の丸め差があります。

```sh
# Nix版：補助モデルを既定のモデルキャッシュへ取得
plamo-download --model 0.8b --weights
plamo-server --model 8b
# ソース版：8Bに加えて0.8Bワーカーもビルド
make MODEL=0.8b all
python3 tools/server.py --model 8b
```

`/health.speculative.enabled`と`block_tokens`で起動時の有効状態と候補数の上限（既定16）を確認します。補助ワーカー・重みがない場合、起動失敗・通信切断時、全層のGPU検証が使えない場合は通常の8B生成へ戻ります。`PLAMO_SPECULATIVE=0`で無効化できます。`PLAMO_SPECULATIVE_TOKENS=2..16`で上限を変更でき、`PLAMO_DRAFT_WORKER`・`PLAMO_DRAFT_DATA_DIR`で補助ワーカーと作業ディレクトリを指定できます。既定では同じビルドの0.8Bワーカー、現在の`models/0.8b`または通常の0.8Bモデルキャッシュを使います。CPU・`--memory stream`・他サイズの通常生成では使いません。

応答の`speculative`は検証バッチ数、消費したトークン数、提案数、採用数、補助処理時間を記録します。提案数・採用数は先頭の既知の8Bトークンを除きます。`timings.decode_steps`は確定した8B状態の更新数で、コマンド数とは異なります。生成速度は補助処理・検証・KV反映を含む`decode_seconds`で測り、HTTPのSSE受信時刻でも確認します。起動と入力処理は別計測です。補助プロセスにも重み・KV・入力処理のメモリが必要です。

```sh
make build/generation-probe
python3 tools/verify_speculative.py --report build/speculative-accuracy.json
python3 tools/verify_speculative_api.py --source --target 20 --repeats 3
```

合成GPUテストでは1〜16候補、逐次コミット、棄却後の通常生成、満杯のスライディングKVを検証します。実モデルの比較は全logits・内部状態を各出力トークンで採取し、通常のFP32生成とトークン列、EOS、長さ制限、キャンセル、要求リセットを照合します。補助Q4は独立したCPUの量子化・復元値と行列演算を比較します。

M2・24 GiBの通常設定を、ready直後から各方向3回・64出力トークンで測定しました。生成速度の中央値は英日21.695、日英21.041 tokens/s、全6要求の最小値は20.719でした。SSE受信時刻でも全要求が20を超えました。起動は11.11秒、入力処理とともに生成速度から除外しています。実モデルの16条件・224個の全状態/logitsベクトルでは、トークン・EOS・キャンセル結果が一致し、最大相対L2誤差は6.725×10⁻⁶でした。[全測定データ](benchmarks/speculative.json)に各要求、メモリ、バイナリとソースのSHA-256を保存しています。温度・電力制限や他アプリの負荷は制御していません。

## 全層のGPU処理

保持済みのMLPは、前正規化→gate/up射影→SwiGLU→down射影→後正規化・残差を一つのコマンドバッファで実行します。FP32の活性値をGPU上で再利用し、RMSNormの二乗和もFP32で並列に集計します。SwiGLUの指数関数の多項式・飽和条件はCPU実装と共通です。重みが保持されていなければ状態を変更せず通常の射影経路へ戻ります。

生成では全層のQKV・出力射影・MLP・出力ヘッドを事前に確認し、専用バッファまたは実行用ファイルで参照可能なら正規化、Q/Kの正規化、RoPE、KV追加・スライド、Attentionを含む1トークン分を一つのコマンドにまとめます。Embeddingの展開とgreedy選択はCPUです。KVは既存の匿名メモリを[Metalのコピーなしバッファ](https://developer.apple.com/documentation/metal/mtldevice/makebuffer%28bytesnocopy%3Alength%3Aoptions%3Adeallocator%3A%29?language=objc)で共有します。GPU専用のKVコピーや、毎トークンのKV転送は作りません。利用中の行数に合わせてページ境界の参照範囲を広げ、262K行の仮想容量全体を常駐させません。

RoPEのcos/sin表は、CPUと同じFP32の角度形成・倍精度の範囲縮小・多項式で起動時に作ります。API上限のプロンプトと生成に使う位置まで準備し、ネイティブ呼び出しでさらに必要なら拡張します。Attentionの内積と値の重み付き和、softmax分母はCPUのFP32加算順序を踏襲します。RMSNormの並列集計とGPUの平方根・除算にはCPUとの丸め差があります。入力処理もQ/K正規化・RoPE・因果Attention・MLPを含めて全層を一つのGPUコマンドにまとめます。Attentionのスコア作業領域は最大16 MiBのタイルで再利用し、4096入力トークンでも入力長の二乗の領域を全頭分確保しません。スライディング境界では、各入力のAttentionが古いKVを参照し終えてから最後の窓を確定します。重み不足時は状態を変更せず既存の経路へ戻り、共有KVから再開できます。`compute.fused_decodes`は全層をまとめて実行した生成ステップ数、`fused_prefills`はまとめた入力処理の回数です。後者の累積値には起動時の固定接頭2方向分も含まれます。

通常の大きな射影も、必要なタイルをすべて保持していれば一つのコマンドにまとめます。`compute.command_buffers`でCPUが完了を待った回数、`fused_mlps`で融合済みMLP数を確認できます。`gpu_dispatches`は個別のカーネル数で、同期回数とは異なります。

## 共有メモリと重みの保持

起動時の圧縮を一度だけ実施して別ファイルへ保存する[実行用重みファイルの事前作成](WEIGHT_CACHE.md)も利用できます。元のBF16値と演算精度を保ち、次回から保存済みのブロックを読み込みます。

専用バッファに収まらない行列も、保存済み圧縮ブロックのmmapをMetalビューで直接参照します。全射影が解決でき、ファイル参照分を含む重み作業領域がGPUの推奨量以内なら、入力処理・生成を全層1コマンドで実行します。ビューは再利用し、メモリ圧が高まった場合や専用コピーが増えた場合に解放します。全範囲の確認はモデルの状態を変える前に行い、欠損や作業領域の超過時は従来の行単位の処理に戻します。

保存済み領域の`pread`は最大64 MiBです。専用コピーの保持予算は増やしませんが、GPUのファイルビューはその予算の外にあり、保持範囲は`compute.disk_cache_mapping_bytes`、GPU確保量は`compute.allocated_bytes`で確認します。生成時の`decode_staged_bytes`は明示的な読み込み量、`decode_mapped_bytes`は直接参照した保存領域の累積量で、物理ディスクの読み出し量ではありません。[実行用重みの条件と測定](WEIGHT_CACHE.md)を参照してください。

Metalが確保した`StorageModeShared`のバッファへ、元BF16を8 MiB以下の`pread`で直接読み込みます。CPUの匿名重みキャッシュとGPU重みの二重コピーを作りません。活性値の入力・出力バッファも再利用します。

8Bの`--memory auto`では、モデル全体と転送領域・パディングがGPUの推奨予算に収まるとき、重みを読み取り専用の整数テクスチャへ転送します。元の全16ビットを保持し、候補検証のタイルへは16ビット整数のまま読み込み、行列演算の直前にFP32へ展開します。転送用の共有コピーは解放し、以降は重みの保持量を固定します。`compute.weight_storage`は`texture-bf16`になります。収まらないデバイスでは従来の適応型キャッシュを使います。`PLAMO_METAL_TEXTURE_WEIGHTS=0`で自動選択を無効にでき、`=1`で明示的に要求できます。明示要求では予算不足時に起動エラーになります。

8Bのテクスチャ経路では転送窓を最大128 MiBにし、8候補の完全なタイルでは境界処理を省きます。ホスト側で行・列・入力の整列とタイルサイズを確認し、それ以外は端数を扱う通常カーネルへ送ります。4分割のFP32集計を含む2 MiBの作業領域を共有します。最大16候補の検証用バッファも起動時に確保してGPUから一度アクセスし、初回要求中の確保を減らします。翻訳文や要求固有のKVを事前計算する処理ではありません。

`PLAMO_METAL_TEXTURE_HEAP=1`を併用すると、デバイスの確保上限内の単一Heapへテクスチャをまとめます。収まらない分は個別に確保し、実際に使われたHeapの確保量を`compute.weight_heap_bytes`に表示します。`PLAMO_METAL_PRIVATE_WEIGHTS=1`は、保持する通常・圧縮・補助Q4バッファをGPU専用領域へ置く別の実験用設定です。`stream`には適用せず、元の重みと演算精度を保ちます。`compute.private_weight_bytes`は、テクスチャを含むGPU専用領域の保持量を元BF16換算で示します。これらの設定は既定では無効です。

8Bのテクスチャ経路以外では、既定の`PLAMO_WEIGHT_STORAGE=auto`は、準備済みの無損失ファイルがある場合、または計算用の元BF16行列がキャッシュ上限に収まらない場合に無損失圧縮を選びます。512値ごとの符号・仮数と指数差をビット列に保存し、行列演算のロード時に全16ビットを復元します。圧縮が有利な1 MiB以上の保持ブロックが対象です。保持領域を節約して、生成中のファイル読み込みを減らします。準備済みファイルがなく、上限に収まるモデルは通常のBF16キャッシュを使います。

`PLAMO_WEIGHT_STORAGE=raw`で通常形式、`lossless`で圧縮形式を明示できます。CPUと`--memory stream`には適用しません。`memory.cached_weight_bytes`は元BF16換算、`cached_storage_bytes`はページ境界の余白を含む保持領域です。後者と`staging_bytes`の合計を`budget_bytes`以下に制限します。`compute.weight_storage`と`packed_weight_bytes`で形式と、圧縮して保持している元のデータ量を確認できます。圧縮後の必要量を記録し、メモリ圧で解放されたブロックが収まらなければ再読み込み・再解析を省きます。

| メモリモード | Metalでの動作 |
| --- | --- |
| `auto` | APIは保持可能な行列を起動時に先読みし、以降の入力処理・生成・別要求で再利用する。単発CLIは最初の入力処理内で保持可能な行列を準備する |
| `resident` | スキーマの2次元BF16テンソルを起動時に共有バッファへ先読みする。収まらなければ起動失敗にする |
| `stream` | 重みを保持せず、1〜64 MiBの共有読み込み領域を再利用する |

テクスチャ以外の`auto`の上限は起動時の再利用可能メモリから2 GiBを引いた量と、GPUの推奨作業領域から128 MiBを引いた量の小さい方です。これを超えて拡張しません。空きが減れば末尾の保持ブロックを解放し、回復すれば起動時の上限内で保持量を増やします。通常のミスでは保持データを追い出さず、モデルの逐次走査で毎回全データが入れ替わることを防ぎます。

prefillとdecodeでI/Oの行境界をそろえます。GPUの処理完了を待ってから共有読み込み領域を上書きし、メモリの調整も未完了のGPU処理がない状態で実行します。BF16ファイルのmmap・FDはCPUのEmbeddingなどにも使うため保持します。GPUの`auto`・`resident`に表示する`preloaded_weight_bytes`は起動時に先読みした行列データ量です。`auto`は推論順にQKV・出力射影・MLP・ヘッドを読み、保持できないタイルを読み飛ばします。通常の保持ブロックはページごとに1バイトを読むカーネルで、圧縮ブロックはGPUでの符号化で初回アクセスを済ませます。完了済みのブロックは再準備しません。さらに小さな正規化重み、正確なRoPE表、再利用するGPU作業領域を起動時に準備します。その後、必要な行列を専用バッファまたは実行用ファイルからGPUで参照できる場合に限り、英日・日英の固定接頭を計算してKVを保存します。本文を含むダミー要求は送らず、論理的な要求状態はリセットしてから`ready`を通知します。

macOS 15以降では[Metal residency sets](https://developer.apple.com/documentation/metal/simplifying-gpu-resource-management-with-residency-sets)に保持中の重み・ファイルビュー・読み込み領域・活性値バッファを登録し、GPUへの常駐を要求します。新しい重み・作業領域の追加登録をGPUコマンドの送信前にまとめて反映します。これは[Appleの`commit`の手順](https://developer.apple.com/documentation/metal/mtlresidencyset/commit())に沿った処理です。メモリ圧での解放時は直ちに登録を反映し、空いたページを保持し続けません。`compute.residency_sets`で有効かを確認できます。古いOSでは通常のMetalリソース管理を使います。

保持量・読み込み量・命中率は従来と同じ`memory`と`weight_io`で確認できます。OS全体のメモリやGPUリソース確保に対する厳密な上限、物理ページ固定を保証する仕組みではありません。8BのBF16は約17 GBあり、空きが少なければGPUを使っても読み込みが律速します。

## 検証

```sh
make test test-tools
make build/test-metal
# GPUがない場合のスキップを許さずに実行
./build/test-metal --require-gpu
./build/test-packing --require-gpu
./build/test-metal-decode --require-gpu
# API・シェーダー検証レイヤーも有効化
MTL_DEBUG_LAYER=1 MTL_SHADER_VALIDATION=1 ./build/test-metal --require-gpu

# 実モデルの全logits・最終状態をCPU/各GPUモードで比較
python3 tools/compare_backends.py --model 2b
python3 tools/compare_backends.py --model 8b
# 64入力トークン以上の文章も--textで指定可能
python3 tools/verify_api.py --backend metal --translate --repeats 3 --report build/metal-api.json
python3 tools/benchmark_decode.py --model 2b --baseline-worker /path/to/previous-worker --report build/decode.json
```

合成テストはFP32で、行・列・トークンの端数、空形状、パディングされたストライド、行分割を検証します。融合MLPはCPU参照と0〜65トークンを照合し、重み未保持・解放時に入力状態を変更しないことも検査します。共有BF16の先読み、別名参照、複数タイルの一括実行、圧力による縮小・回復、不完全な読み込みからの復旧、終了後の再初期化も検証します。

圧縮と整数テクスチャはNaN・無限大・非正規化数・符号付きゼロを含むBF16の全65,536通りをGPU上でビット単位に照合します。整数テクスチャはGPU用の最適化後も、行の直接参照・線形参照・別名参照が完全一致することを検査します。圧縮は指数幅0〜8、端数、オフセットも照合し、圧縮あり・なしの行列演算のFP32出力をビット単位で比較します。全層の入力処理・生成ではCPUの行列演算・正規化・Attentionを参照とし、共有KV、スライド、128行を超える拡張、古い回転済みKの再構築、1〜4096トークンのバッチ入力処理、16 MiB作業領域の再利用、要求リセット、メモリ圧後の復帰、満杯のグローバルKVで状態を変更しないことを検証します。

実モデルの比較ツールはCPUに対する最大絶対誤差・RMS誤差・相対L2誤差と、選ばれるトークンを記録します。相対L2誤差の検査上限はすべて`1e-4`です。これは数値実装の回帰検査で、あらゆる文章での翻訳品質や生成トークンの一致を保証する基準ではありません。

検証機はApple M2・24 GiB・macOS 26.5.1です。31Bはビルドと合成ローダーの検証までで、実翻訳は未検証です。GPUにアクセスできないCIやサンドボックスではGPUテストを明示的にスキップし、CPUテストを実行します。シェーダーのソースは実行ファイルへ埋め込んで実行時にコンパイルするため、利用時に`metal`コンパイラーコマンドを別途インストールする必要はありません。NixはSDK 15以上を選び、常駐管理APIをビルドに含めます。

## 入力処理全体のGPU化と固定接頭の再利用

Apple M2・24 GiB・FP32で、起動完了直後にウォームアップ要求を送らず比較しました。各条件3プロセス、前後の実行順を交互にし、初回トークン到着の中央値です。0.8B・2Bは通常BF16、8Bは前後で同じ可逆圧縮・同じ保持量です。測定した要求中の大行列の明示的な読み込みはすべて0でした。

| 条件 | 変更前 | 変更後 | 時間短縮 |
| --- | ---: | ---: | ---: |
| 0.8B・21入力・通常BF16 | 0.093秒 | 0.029秒 | 68.2% |
| 2B・21入力・通常BF16 | 0.217秒 | 0.100秒 | 53.9% |
| 8B・21入力・可逆圧縮BF16 | 0.657秒 | 0.404秒 | 38.5% |
| 2B・81入力・通常BF16 | 0.572秒 | 0.376秒 | 34.3% |
| 8B・81入力・可逆圧縮BF16 | 1.867秒 | 1.490秒 | 20.2% |

入力処理全体のCPU同期を0.8Bで49→1回、2Bで73→1回、8Bで97→1回に減らしました。短い入力には8/16/24トークンの専用行列積を使い、長い入力でも重みを読む回数を増やさず余白が最も少ないタイルを選びます。例えば固定接頭を省いた69トークンには、32×3ではなく24×3のタイルを使います。

常駐APIは起動時に英日・日英の固定接頭12トークンを計算します。この追加準備は2Bで約0.21秒、8Bで約0.8秒で、`load_seconds`・`preload_seconds`にも含みます。要求時はトークン列の完全一致を確認してから不変のKVを復元し、残りを毎回計算します。本文・翻訳結果のキャッシュではありません。8Bの追加領域は約4.7 MBです。`PLAMO_PREFIX_CACHE=0`で無効化できます。単発CLIは2方向の接頭を事前計算しません。

入力処理のGPU化、固定接頭の有無とも、FP32の演算・元BF16の全ビットを維持します。3モデルの21/81入力トークンでCPU参照に対する全logits・最終状態の最大相対L2誤差は`3.25e-6`未満でした。固定接頭の有無を切り替えた各10要求では、状態・logitsの全体ハッシュ、生成トークンとテキストがビット単位で一致しました。英日・日英の切り替え、長文、予約トークン、通常の生成を含みます。2Bの完了した英日・日英6文でもCPU/GPUの全トークンとテキストが一致しました。実HTTP SSEでは2Bの初回トークンを約0.102秒で受信し、接頭再利用の報告も確認しました。

比較対象は変更前コミット`2f3bcf7`の保存済み実行ファイルです。各回の起動・初回・2回目、保持量・I/O、ソースとバイナリのハッシュ、数値比較、不採用の試行は[初回応答の測定結果](benchmarks/ttft.json)に保存しています。起動時間と要求後の時間を区別し、メモリ圧やOSのキャッシュで変動する点も確認してください。

```sh
python3 tools/benchmark_startup.py --model 2b --backend metal --memory resident --baseline-worker /path/to/previous-worker --repeats 3
python3 tools/benchmark_startup.py --model 8b --backend metal --memory auto --storage lossless --baseline-worker /path/to/previous-worker --repeats 3
python3 tools/verify_prefix_cache.py --model 2b --memory resident
python3 tools/verify_prefix_cache.py --model 8b
```

## 全層生成・無損失キャッシュの実測

Apple M2・24 GiBで、81入力トークンから先頭24出力トークンを生成し、入力処理を除いた23生成ステップを計測しました。2トークンのウォームアップ後に3要求の中央値を比較しています。いずれも双方が同じ計算用行列を保持でき、測定した要求中の明示的な重み読み込みは0でした。0.8B・2Bは通常BF16、8Bは双方とも同じ無損失キャッシュです。GPU演算は双方FP32です。

| モデル | 生成速度：前→後 | 改善 | 生成1ステップの同期：前→後 |
| --- | ---: | ---: | ---: |
| 0.8B | 28.35→49.38 tokens/s | 74.2% | 49→1回 |
| 2B | 10.70→14.98 tokens/s | 40.0% | 73→1回 |
| 8B | 4.30→5.48 tokens/s | 27.6% | 97→1回 |

変更後はGPUコマンドの実行時間が生成経過時間の約98〜99%を占めています。8Bの計算用行列は元BF16の16,181,624,832バイトに対し、保持領域が12,295,471,104バイトでした。圧縮の有無で比較した別の実行では0.77→4.21 tokens/sでしたが、利用可能メモリも異なり、通常形式の一部読み込みと圧縮形式の全保持の違いを含みます。これは上の同量保持比較と別の測定です。

ウォームアップなしの`Hello.`の初回トークンは、2Bで0.291→0.202秒、8Bで1.374→0.660秒でした。起動は2Bで1.156→1.132秒、8Bで6.640→8.445秒です。8Bでは先読み・圧縮を起動へ移し、保持量も増えています。準備完了後の初回応答と起動時間の両方を確認してください。

0.8B・2B・8Bの21/81入力トークンで、全logits・最終状態のCPU参照に対する最大相対L2誤差は`3.54e-6`未満でした。各測定の前後で生成トークン列が一致し、2Bの英日3文・日英3文の完了した翻訳でもCPU/GPUの全トークンIDとテキストが一致しました。数値・各回・保持量・固定リビジョン・バイナリとソースのハッシュは[生成と初回応答の測定結果](benchmarks/decode.json)に保存しています。

## FP32統一・同期削減の実測

Apple M2・24 GiBで、変更前の保存済みワーカーを`metal-fp32`に固定し、変更後もFP32で順に比較しました。初期読み込み・トークナイザー照合・キャンセルしたウォームアップを除き、短文の常駐条件は5回、長文と8Bの都度読み込み条件は3回の中央値です。短文は21入力トークン・1出力トークンと停止までの1生成ステップ、長文は81入力トークン・先頭12出力トークンです。

| 条件 | 変更前 | 変更後 | 時間短縮 |
| --- | ---: | ---: | ---: |
| 0.8B・`resident`・短文 | 0.165秒 | 0.120秒 | 27.1% |
| 2B・`resident`・短文 | 0.544秒 | 0.362秒 | 33.5% |
| 2B・`resident`・長文の先頭12トークン | 2.094秒 | 1.809秒 | 13.6% |
| 8B・`stream`・短文 | 9.721秒 | 8.726秒 | 10.2% |

常駐条件の要求中の重み読み込みは双方0、8Bの`stream`は双方32,363,249,664バイトでした。8Bの生成は約3.62秒で、ここではディスクI/Oが引き続き律速します。2Bの短文の入力処理は0.442秒→0.265秒でした。各要求の生成トークン列は変更前後で一致しています。

8Bの`auto`は3.219秒→2.073秒でしたが、保持量は約12.96 GB→14.18 GB、要求中の読み込み量は約6.44 GB→4.01 GBと異なります。空きメモリによる条件差を含み、上の同量I/O比較とは区別します。完全に保持できる場合でも元BF16の帯域を使うため、量子化されたLM Studioモデルと同じ速度を保証するものではありません。

2Bの21/81入力トークンと8Bの21入力トークンで、全logits・最終状態のCPU参照に対する最大相対L2誤差は`3.23e-6`未満でした。2Bの完了した英日3文・日英3文では、全生成トークンIDとテキストが一致しました。`tools/compare_translations.py --model 2b --memory resident`で再検証できます。数値・各回・元重みの固定リビジョン・バイナリとソースのハッシュは[FP32最適化の測定結果](benchmarks/fp32-fused.json)に記録しています。

## 過去の測定（MLP融合前）

同じM2でCPU 4スレッドとMetalを順に実行し、初期読み込み・トークナイザー検査・キャンセルした入力処理を除く3要求の中央値を比較しました。短文は`Hello.`の21入力トークンと1回の生成計算、長文は81入力トークンと先頭12生成トークンです。測定中に別のベンチマークは実行していません。

| 条件 | CPU・要求全体 | Metal・要求全体 |

| 2B・`resident`・短文 | 0.545秒 | 0.543秒 |
| 2B・`resident`・長文の先頭12トークン | 2.731秒 | 1.895秒 |

8Bの`stream`は両条件とも要求中に32,363,249,664バイトを明示的に読み込み、約1.48倍でした。`auto`は約3.58倍ですが、CPUは約14.59 GBを保持して要求中に約3.19 GBを読み込み、GPUは計算用の約16.18 GBをすべて保持して明示的な読み込みが0でした。起動時の空きと保持量が違うため、この倍率をGPU演算だけの効果とは扱えません。GPUの生成1ステップは中央値約0.268秒でした。
